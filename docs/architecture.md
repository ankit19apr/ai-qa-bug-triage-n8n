# Architecture – AI QA Bug Triage Automation

## 1. Purpose

The **AI QA Bug Triage Automation** project demonstrates how n8n can be used to automate a QA defect-triage workflow.

The current MVP accepts a structured bug report through a webhook, normalizes the data, performs simulated QA triage, checks for duplicate bugs, and routes the request either to a duplicate response or to a simulated Jira creation flow.

---

## 2. High-Level Architecture

```text
Postman / Bug Reporter
        |
        v
   n8n Webhook
        |
        v
    Edit Fields
        |
        v
Mock AI Triage Result
        |
        v
 Duplicate Check
        |
        v
   Is Duplicate?
      /       \
    YES        NO
     |          |
     v          v
Handle       Prepare
Duplicate    New Bug
     |          |
     v          v
Final       Mock Jira
Response      Create
                |
                v
          Final Response
```

---

## 3. Input Layer

The workflow starts with an n8n **Webhook** node.

### HTTP Method

```text
POST
```

### Webhook Path

```text
ai-qa-bug
```

The webhook accepts a JSON bug report.

Example:

```json
{
  "title": "Login button not working",
  "description": "User enters valid username and password, but clicking the Login button does nothing.",
  "steps": [
    "Open the login page",
    "Enter valid username",
    "Enter valid password",
    "Click Login"
  ],
  "expected": "User should be redirected to the dashboard.",
  "actual": "Nothing happens after clicking Login.",
  "environment": "Chrome 153 on Windows 11"
}
```

---

## 4. Data Normalization

The **Edit Fields** node transforms the incoming webhook payload into a clean internal structure.

The workflow extracts:

```text
bugTitle
description
expectedResult
actualResult
environment
steps
```

This creates a consistent structure for downstream processing.

---

## 5. QA Triage Layer

The current MVP contains a **Mock AI Triage Result** node.

It simulates the structured output that would eventually be generated by an AI model.

Example:

```json
{
  "category": "Functional",
  "severity": "High",
  "priority": "High",
  "component": "Login",
  "summary": "Login button does not respond after valid credentials",
  "investigationReady": true
}
```

### Why use a mock?

The MVP can be developed and tested without requiring a paid external LLM API.

The workflow also contains an **AI Agent**, an OpenAI Chat Model configuration, and a Structured Output Parser for the next development phase.

---

## 6. Duplicate Detection

The **Duplicate Check** code node compares the incoming bug against a simulated list of existing bugs.

The current MVP uses an exact comparison based on:

```text
Bug Title + Component
```

Example existing bug:

```json
{
  "bugTitle": "Login button not working",
  "component": "Login"
}
```

If both the title and component match, the workflow marks the bug as a duplicate.

The node produces:

```json
{
  "duplicateFound": true,
  "duplicateStatus": "DUPLICATE"
}
```

For a non-matching bug:

```json
{
  "duplicateFound": false,
  "duplicateStatus": "NEW"
}
```

---

## 7. Conditional Routing

The **Is Duplicate?** IF node evaluates:

```text
duplicateFound == true
```

### Duplicate Branch

```text
Is Duplicate?
      |
     YES
      |
      v
Handle Duplicate
      |
      v
Final Response - Duplicate
      |
      v
Respond to Webhook
```

The workflow does not create a new Jira ticket for the duplicate path.

Example response:

```json
{
  "result": "DUPLICATE",
  "jiraKey": "DUPLICATE_NOT_CREATED",
  "severity": "High",
  "priority": "High",
  "summary": "Login button does not respond after valid credentials",
  "message": "Duplicate bug detected. No new Jira ticket created."
}
```

---

## 8. New Bug Branch

When the bug is not identified as a duplicate:

```text
Is Duplicate?
      |
      NO
      |
      v
Prepare New Bug
      |
      v
Mock Jira Create
      |
      v
Final Response - New Bug
      |
      v
Respond to Webhook
```

The **Prepare New Bug** node creates Jira-ready information containing:

- Bug description
- Steps to reproduce
- Expected result
- Actual result
- Environment
- Category
- Severity
- Priority
- Component

---

## 9. Jira Simulation

The current MVP uses **Mock Jira Create** rather than a live Jira API.

Example simulated output:

```json
{
  "jiraKey": "QA-1001",
  "status": "CREATED",
  "project": "QA"
}
```

The final response returns:

```json
{
  "result": "NEW_BUG_CREATED",
  "jiraKey": "QA-1001",
  "severity": "High",
  "priority": "High",
  "summary": "Login button does not respond after valid credentials",
  "message": "Bug created successfully"
}
```

---

## 10. Response Layer

The workflow uses **Respond to Webhook** nodes to return the final JSON response to the caller.

There are two outcomes:

```text
DUPLICATE
```

or

```text
NEW_BUG_CREATED
```

This makes the workflow usable as an API-style automation endpoint.

## 11. Current MVP Components

| Component | Current Implementation |
|---|---|

| Data transformation | Edit Fields |
| AI triage | Mock AI Triage Result |
| Duplicate detection | JavaScript code |

| Jira preparation | Edit Fields |

## 12. Planned Evolution

### Phase 2 – Real AI Triage

Replace:

```text
Mock AI Triage Result
```

with:

```text
AI Agent
   |
   v
LLM
   |
   v
Structured Output
```

The AI will dynamically analyze incoming bug reports and generate fields such as severity, priority, component, category, and summary.

---

### Phase 3 – Real Jira Integration

Replace:

```text
Mock Jira Create
```

with a real Jira integration.

Target flow:

```text
New Bug
   |
   v
Prepare Jira Payload
   |
   v
Jira API
   |
   v
Real Jira Issue Key
```

---

### Phase 4 – Semantic Duplicate Detection

The current exact title/component comparison can evolve into semantic duplicate detection.

Target architecture:

```text
New Bug
   |
   v
Create Embedding
   |
   v
Search Historical Bugs
   |
   v
Similarity Analysis
   |
   v
Potential Duplicate?
```

---

### Phase 5 – Playwright Failure Integration

The workflow can eventually consume automated test failures.

Target flow:

```text
Playwright Test
       |
       v
Test Failure
       |
       +---- Screenshot
       |
       +---- Stack Trace
       |
       +---- URL
       |
       +---- Browser
       |
       v
      n8n
       |
       v
   AI Analysis
       |
       v
Root Cause Analysis
       |
       v
    Jira Bug
```

This would extend the project from manual bug triage into automated **test-failure-to-defect automation**.

---

## 13. Long-Term Vision

The long-term objective is to build an AI-assisted QA workflow capable of supporting:

```text
Manual Bug Reports
        +
Automated Test Failures
        |
        v
       n8n
        |
        v
   AI QA Agent
        |
        +--> Bug Triage
        |
        +--> Duplicate Detection
        |
        +--> Root Cause Analysis
        |
        +--> Test Failure Analysis
        |
        v
      Jira
        |
        v
 Notifications / QA Reporting
```

The project is intentionally being developed incrementally, starting with a working MVP and adding real AI, Jira, semantic search, and Playwright integrations in later phases.
